## Откуда всё началось

Представьте, что вы смотрите на изображение. Ваш взгляд перемещается от одного пятна к другому. Каждое движение глаза — это не просто «посмотрел туда», это переход: яркое пятно сменилось тёмным, крупный объект уступил место мелкому, гладкая текстура стала зернистой.

Вот ключевое наблюдение, с которого начался этот проект (BTR R&D, 2014): **не важно, ЧТО изображено. Важны направленные переходы между характеристиками областей.** Котёнок или грузовик — это разные объекты, но кривая, по которой взгляд скользит по ним, может быть похожей. А значит, паттерн — узнаваем.

Это и есть «признак» — не пиксель, не объект, а **переход**:

```python
@dataclass
class FeatureVector:
    delta_size:       float  # стало больше или меньше?
    delta_brightness: float  # стало светлее или темнее?
    delta_contrast:   float  # стало контрастнее?
    delta_color_hue:  float  # сменился оттенок?
    delta_color_sat:  float  # насыщенность?
    delta_fractal_dim: float # сложность текстуры?
```

Ключевое свойство: этот вектор **инвариантен к аффинным преобразованиям**. Сдвиньте изображение, поверните, измените масштаб — переход «от яркого к тёмному» останется «от яркого к тёмному». Именно это позволяет узнавать паттерны вне зависимости от того, где и в каком виде они встречаются.

## От изображений к тексту

Идея оказалась шире, чем картинки. Если признак — это направленный переход между характеристиками области, то и **слово в тексте** можно закодировать как «область» с характеристиками. Тогда переход «слово за словом» — это тоже признак.

Вот как TextDriver кодирует слово:

```python
def _word_to_region(word: str, vocab_index: float) -> RegionCharacteristics:
    length     = min(len(word) / 20.0, 1.0)   # «размер» = длина слова
    complexity = len(set(word)) / len(word)    # «контраст» = доля уникальных букв
    return RegionCharacteristics(
        size=length,
        brightness=vocab_index,   # место в словаре по частоте
        contrast=complexity,
        color_hue=vocab_index,
        fractal_dim=1.0 + complexity,
    )
```

Слово «кот» — короткое, простое, частое. Слово «хозяйственный» — длинное, богатое уникальными буквами, редкое. Переход между ними кодируется как вектор изменений всех этих характеристик. И этот вектор будет похожим всякий раз, когда в тексте за коротким частым словом следует длинное сложное — независимо от конкретных слов.

## Главная идея: обобщение как цепочка признаков

Один переход ничего не говорит. Но цепочка переходов — это уже паттерн.

Если система видела много раз:
```
«Маша» → «пришла» → «к» → «Саше»
```
и каждый раз это подтверждалось — у неё формируется **обобщение (Gen)**: цепочка признаков этих четырёх переходов. В следующий раз, увидев начало знакомого перехода, система *ожидает* продолжение.

```python
@dataclass
class Generalization:
    gen_id:        str
    feature_chain: List[str]  # упорядоченный список feature_id
    success_count: int = 0    # сколько раз подтверждалось
    stop_count:    int = 0    # сколько раз опровергалось

    @property
    def significance(self) -> float:
        total = self.success_count + self.stop_count
        return self.success_count / total if total > 0 else 0.0
```

`significance` — это не просто счётчик. Это **ранг в опыте**: соотношение успехов к неудачам. Gen, который подтверждается 9 раз из 10 (significance=0.9), гораздо весомее того, что подтверждается 5 раз из 10 (significance=0.5).

## Главный алгоритм: три исхода

Каждый входящий токен порождает один из четырёх исходов:

```
Новый токен
    │
    ├── Есть ожидание в контексте?
    │       │
    │       ├── Да → Совпадает с ожиданием? ──► CONFIRMED (продолжить цепочку)
    │       │                              └──► REFUTED   (удивление, создать новый Gen)
    │       │
    │       └── Нет → EXPLORING (исследовать окрестности)
    │
    └── Ожидание полностью исполнилось? ──► COMPLETED (цепочка завершена, успех)
```

Вот реальный вывод системы во время обучения на тексте «Винни-Пух живёт в лесу рядом с большим дубом»:

```
токен "Винни-Пух"  → EXPLORING    (контекст пуст, начинаем)
токен "живёт"      → REFUTED      (нет ожидания, но создаём Gen G1: [f_Винни→живёт])
токен "в"          → CONFIRMED    (G1 продолжается: [f_Винни→живёт, f_живёт→в])
токен "лесу"       → CONFIRMED    (G1 растёт...)
токен "рядом"      → REFUTED      (что-то изменилось, G1 прерван, новый G2)
...
```

При втором прочтении той же фразы:
```
токен "Винни-Пух"  → EXPLORING
токен "живёт"      → CONFIRMED  (G1 узнан!)
токен "в"          → CONFIRMED
токен "лесу"       → CONFIRMED
токен "рядом"      → CONFIRMED
...                → COMPLETED  (G1 полностью подтверждён, significance растёт)
```

После достаточного числа повторений G1 становится **прочным**: его `significance` приближается к 1.0, он начинает загружаться в контекст автоматически, как долгосрочная гипотеза о мире.

## Гетерархия, а не иерархия

Ключевое архитектурное решение: обобщения не организованы в дерево «сверху вниз». Они организованы в **гетерархию** — плоскую сеть, где Gen могут ссылаться друг на друга с любого уровня.

Почему не иерархия? Потому что в реальном познании «кошка» и «животное» не находятся строго одно над другим. «Кошка» — это конкретный Gen, «животное» — более общий, но они пересекаются с «домашний питомец», «существо с усами», «Мурка» — и все эти связи горизонтальные.

В коде это выглядит так:

```python
# Gen «Пух → мёд» (конкретный, chain=2)
G_honey = Generalization(
    gen_id="g-honey-001",
    feature_chain=["f_Пух→любит", "f_любит→мёд"],
    success_count=14, stop_count=2,
    label="пух·мёд"
)

# Gen «любит → [что-то]» (абстрактный, chain=1)
G_likes = Generalization(
    gen_id="g-likes-001",
    feature_chain=["f_любит→X"],
    success_count=31, stop_count=5,
    parent_ids=[],
    child_ids=["g-honey-001", "g-морковь-001", "g-прыгать-001"]
)
```

Через общий префикс «любит→X» система *автоматически* обнаруживает, что мёд, морковь и прыгание — разные конкретизации одной абстракции. Это и есть консолидация: общие префиксы подтверждённых Gen → мета-Gen.

## Первые корпуса: от бинарных петель к нарративу

Самый первый корпус для обучения выглядел так:

```python
_CORPUS = {
    1: [  # LEVEL 1: максимальная предсказуемость
        "день ночь день ночь день ночь день ночь",
        "утро вечер утро вечер утро вечер утро вечер",
        "вдох выдох вдох выдох вдох выдох вдох выдох",
    ],
    2: [  # LEVEL 2: ритмичные паттерны
        "кот сидит на окне кот сидит на диване кот сидит на окне",
        "весна лето осень зима весна лето осень зима весна",
    ],
    3: [  # LEVEL 3: нарративные последовательности
        "утром встал умылся позавтракал пошёл на работу вернулся поужинал лёг спать",
        "увидел проблему подумал нашёл решение применил увидел результат обрадовался",
    ],
    4: [  # LEVEL 4: с развилками
        "пришёл домой лёг отдохнул встал поел пошёл гулять вернулся лёг",
        "пришёл домой лёг отдохнул встал поел остался дома почитал книгу",
    ]
}
```

Это намеренная лесенка сложности. На уровне 1 система быстро строит прочные Gen — «день→ночь→день» подтверждается с почти единичной значимостью. На уровне 3 Gen длиннее и сложнее. На уровне 4 одна и та же ситуация может завершиться по-разному: «пошёл гулять» или «остался дома». Система должна учиться держать обе ветки как конкурирующие гипотезы.

## Проблема «Дома который построил Джек»

Первая серьёзная проблема обнаружилась на корпусе из детской песни — «Дом который построил Джек». Текст с накапливающимися повторами:

```
Вот дом который построил Джек
Вот пшеница которая в тёмном чулане хранится в доме который построил Джек
Вот кошка которая пугает и ловит синицу которая часто ворует пшеницу...
```

После 1000 циклов обучения база Gen разрослась до **14 000 обобщений**. Большинство — шум: уникальные однократные паттерны, которые больше никогда не встретятся. Система тратила время на сравнение каждого нового токена с 14K кандидатами.

Это был диагноз: при REFUTED система немедленно создавала Gen — без какого-либо «испытательного срока». Любой единственный неожиданный переход становился полноправным обобщением.

### Решение: ProvisionalBase

Ввели механизм испытательного срока:

```python
class ProvisionalBase:
    """
    min_confirmations = 2   — нужно хотя бы 2 подтверждения
    max_age           = 30  — 30 шагов без подтверждений → выброс
    """

    def track(self, gen_id: str):
        # новый Gen попадает под наблюдение
        self._entries[gen_id] = ProvisionalEntry(gen_id=gen_id)

    def confirm(self, gen_id: str) -> bool:
        # подтверждение → считаем; True = promoted (снят с испытания)
        entry = self._entries.get(gen_id)
        if entry:
            entry.confirmations += 1
            if entry.confirmations >= self.min_confirmations:
                del self._entries[gen_id]
                return True  # promoted!
        return False

    def tick(self) -> List[str]:
        # каждый шаг → стареем; истёкшие → список на удаление
        to_evict = []
        for gen_id, entry in list(self._entries.items()):
            entry.age += 1
            if entry.age > self.max_age and entry.confirmations == 0:
                to_evict.append(gen_id)
        ...
        return to_evict
```

Результат на корпусе Винни-Пуха с `ProvisionalBase(min_confirmations=2, max_age=200)`: база стабилизировалась на ≤3K Gen вместо 14K+.

Важное открытие: `max_age` должен быть **больше длины одного цикла корпуса**. Для Винни-Пуха (11 текстов × ~8 слов = 88 шагов) нужен max_age=200: иначе система выбрасывает Gen, которые просто не успели встретиться во второй раз.

## H1–H5: Первый цикл гипотез — «Витальность»

Когда база работала стабильно, появился следующий вопрос: **как система знает, что ей нужно освежить контекст?** Если Gen сформировался месяц назад и с тех пор не активировался — он всё ещё актуален?

Мы ввели понятие **витальности** — «живости» обобщения:

```
urgency  = elapsed / mean_interval      (сколько «ждёт» по сравнению с обычным ритмом)
vitality = significance × exp(-max(0, urgency - 1.0))
```

Gen с urgency < 1 — «спит спокойно», всё в порядке. При urgency > 1 начинается «беспокойство»: витальность падает экспоненциально. При urgency = 10 — Gen буквально «кричит», что про него забыли.

Идея аналогична буддийским дхармам, которые «стучатся в ворота сознания». Или — на языке нейробиологии — следовым кондиционированием: давно не активированный паттерн «напоминает о себе».

**Гипотезы H1–H5** были первой попыткой проверить, работает ли это:

| # | Что проверяли | Ожидание | Результат |
|---|--------------|---------|-----------|
| H1 | Ритм активаций ≈ 13 шагов (длина предложения) | avg_interval=13 | avg_interval=2.0 ← **сюрприз** |
| H2 | WakeUp ускоряет работу (реанимирует контекст) | speedup > 1.5× | speedup=1.00× |
| H3 | Сторожок: есть Gen с urgency > 2.0 | knock_candidates > 0 | 13 кандидатов ✓ |
| H4 | База Gen стабилизируется (перестаёт расти) | plateau к итерации 5 | plateau с итерации 5 ✓ |
| H5 | Vitality выше ВНУТРИ текста, чем ПОСЛЕ | fraction > 70% | fraction=60% |

**Инсайт H1** оказался самым неожиданным: система работает на **токен-гранулярности**, а не на предложениях. Каждое слово — отдельный шаг. Между «Маша» и «пришла» проходит один шаг, не тринадцать. Поэтому средний интервал оказался 2.0, а не 13.

**Инсайт H2** был первым сигналом более глубокой проблемы: WakeUp (механизм реанимации) не даёт ускорения, потому что на знакомом корпусе система и так работает оптимально. Ускорение можно заметить только на *незнакомом* материале после паузы.

## H6–H10: Второй цикл — «Парадокс умного учителя»

Продолжая исследовать витальность, мы задались вопросом: **в каком порядке лучше подавать тексты?** Интуиция говорила: начинать с самых сложных (там система учится больше всего).

**Гипотеза H7** — «knock-curriculum»: сначала подаём тексты с наихудшим match rate (тексты, которые система плохо знает).

```
knock-curriculum: сначала худшие тексты → много REFUTED → система учится
random:           случайный порядок → смешивание лёгкого и сложного
```

Результат: **knock-curriculum оказался на 52.7% хуже random порядка**.

Это был «парадокс умного учителя» — второй раз (первый был раньше, на другом корпусе). Объяснение оказалось простым: если начинать с худших текстов, система получает лавину REFUTED-событий. Каждое удивление создаёт новый Gen-кандидат. Но кандидаты не подтверждаются — следующие тексты тоже непонятны. В результате база заполнена шумом, а система «деморализована».

Random порядок работает лучше, потому что лёгкие тексты дают системе **импульс** — цепочку подтверждений, которая укрепляет базовые Gen. С этой основой система легче справляется со сложными.

**Правильная стратегия (вывод H7)**: сначала «якорные» тексты (лёгкие, хорошо знакомые), потом постепенно сложнее. Не умный учитель, а *добрый* учитель.

**Инсайт H10** раскрыл смысл urgency: это не предиктор «скоро REFUTED», а предиктор «нужен ли WakeUp». Gen с высоким urgency = Gen, который давно не подтверждался. Это значит, что его контекст не загружен — и WakeUp должен его восстановить. Но это не значит, что следующий токен окажется для него неожиданным.

## H11–H15: Третий цикл — «Ёмкость и деградация»

К этому моменту стала очевидна принципиальная проблема: **сколько Gen может система держать без деградации?**

Была предложена модель N^M:

```
N = ветвление на каждом уровне (≈ 7±2, число Миллера)
M = глубина (число уровней обобщения)

Рабочая ёмкость:
  5^5  =  3,125  — нижняя граница
  6^6  = 46,656  — необычная экспертиза
  8^8  = 16M     — теоретический предел
```

Это не просто метафора. Каждый уровень — это «пул слотов внимания». На первом уровне ≈7 долгосрочных Gen (вещи вроде «сейчас весна», «я в лесу», «Пух ищет мёд»). На втором уровне ≈7 × 7 = 49 среднесрочных. И так далее.

**H11** проверяла, помогает ли жёсткий лимит (CapacityBudget): будет ли средняя значимость Gen выше, если принудительно держать базу ≤6000?

```python
class CapacityBudget:
    def enforce(self, base, scheduler) -> int:
        if base.size() <= self.target_size:
            return 0
        candidates = scheduler.eviction_candidates(base)
        evicted = 0
        for gen_id in candidates:
            if base.size() <= self.target_size:
                break
            base.remove(gen_id)
            evicted += 1
        return evicted
```

Результат H11: **опровергнута** — потому что тестовая база (1013 Gen) ещё не достигла «стены» 5^5=3125. Лимит не давил, значит и эффект был нулевой. Это само по себе важный вывод: CapacityBudget нужен только после определённого порога.

**H13 и H14 подтверждены**: Gen с цепочкой ≥3 (конкретные, «мемуары ситуаций») активируются **исключительно в своём домене** (100% isolation). И Gen с высоким urgency действительно требуют больше шагов без WakeUp — urgency = индикатор нагрузки на контекст.

## H16–H26: Масштаб, DualDriver, и «Сон»

К этому этапу система работала стабильно на малых корпусах. Пришло время **масштабного теста**: 100K–1M переходов, несколько доменов.

### Открытие структурного обучения (H16)

TextDriver обучил систему идеально (MR transfer = 1.0) при смене домена — что казалось неожиданным. Как может система так хорошо переносить знания?

Ответ: **система учит структуру, а не семантику**. TextDriver кодирует переходы через *позицию в словаре* и *сложность слова*, не через смысл. Паттерн «короткое частое слово → длинное редкое слово» встречается в любом тексте на любую тему. Это и есть универсальная структура языка.

Это не недостаток — это фундаментальный инсайт об инвариантности признакового пространства.

### DualDriver: два голоса в диалоге (H19–H24)

Параллельно развивалась идея **двух каналов обучения**:

```
Канал A (молчаливый): внутренний поток Gen-активаций
                      process_token() → CONFIRMED / REFUTED / COMPLETED

Канал B (речевой):    SmartTextDriver интерпретирует ожидания системы
                      «Система ожидала Х, получила Y. Новое обобщение?»
```

DualDriver вводит три метрики:
- `≡ CONV` (convergence) — система и SmartDriver сошлись: оба предсказали слово
- `↺ RECALL` — система знает, SmartDriver не предсказал (или наоборот)
- `✦ DISC` (discovery) — ни система, ни SmartDriver не ожидали: чистое удивление

**H22 подтверждена** блестяще: в знакомом домене среднее число кандидатов-слов, которые система держит как «возможные продолжения», = **4.5–5.7**. Это число Миллера (7±2) на лексическом уровне! Незнакомый домен даёт 2.0–3.4 — система «чувствует» неопределённость и сужает ожидания.

**H21 подтверждена**: при смене домена пик `✦ DISC` достигает 0.54 — больше половины переходов оказываются полным сюрпризом. Это субъективный опыт «попал в незнакомую обстановку».

**H24' (переформулированная)**: вместо ожидаемой S-образной сигмоиды обнаружили «зубья пилы»: каждая смена домена → пик ↺+✦, потом быстрый рост ≡. С каждым новым доменом пик чуть ниже — система всё быстрее адаптируется. Это богаче, чем гипотеза.

### «Дом который построил Джек» — история про CapacityBudget (H18)

При длинном прогоне (100K переходов, 4 домена) без CapacityBudget база росла бесконечно и система замедлялась в 5× (623 tok/s → 115 tok/s при базе 6K Gen).

CapacityBudget остановил это: база = 6000 Gen, MR сохранена. Но появился неожиданный феномен: при пределе 6000 за 1 миллион переходов система **создаёт и выбрасывает 180–240K Gen** — постоянный «чёрновик». Долгосрочная память непрерывно переписывается.

## H25 vs H26: Что такое «сон» на самом деле

Это, пожалуй, самый важный поворот всего проекта.

### H25: провал «скучного сна»

**Гипотеза H25**: если после длительного обучения запустить `sleep_cycle()` (режим консолидации, который воспроизводит уже изученные Gen), то chain≥3 Gen станет больше — система «переварит» опыт.

Реализация:
```python
class ReplayEngine:
    def replay(self, gen_ids, system):
        for gen_id in gen_ids:
            gen = system.base.get(gen_id)
            for feature_id in gen.feature_chain:
                # воспроизводим ожидаемые feature_id активных Gen
                token = self._feature_to_token(feature_id)
                system.process_token(token)
```

Результат: `commit_rate = 0%`. Ни одного нового Gen не создано.

**Почему?** ReplayEngine воспроизводит *ожидаемое*. Ожидаемое всегда подтверждается. CONFIRMED не создаёт новых Gen — он только укрепляет существующие. Получился буквально «скучный сон»: система видит то, что уже знает, и не узнаёт ничего нового.

### H26: «Сон из непонятого»

Это принципиально другая идея. Что если во сне система воспроизводит не **известное**, а **непонятое**?

Вводим `ContextQueryLog` — «лог удивлений дня»:

```python
@dataclass
class REFUTEDEvent:
    feature_id: str      # какой признак удивил
    removed_gen_ids: List[str]  # какие Gen были опровергнуты
    token_label: str     # конкретное слово
    chain_len: int       # на какой глубине контекста это произошло
    urgency: float = 0.0 # повышается при повторном REFUTED
```

Протокол эксперимента:
1. Обучаем систему на **домене А** (лес): тексты про деревья, зверей, тропинки
2. Собираем лог удивлений: какие переходы оказались REFUTED
3. Обучаем на **домене Б** (горы): тексты про вершины, перевалы, встречи
4. Запускаем `SleepDriver.run()`: воспроизводим события из лога А в новом, расширенном контексте

Результат H26 **подтверждён**:

> Событие «лесу→встретил» было REFUTED утром в лесу.
> Ночью, после обучения на горах (где «встретил» тоже встречается),
> это же событие стало COMPLETED.
> Создан мета-Gen chain=30 с domains=[горы, лес].

Это буквально «понять во сне»: связи, которые не складывались в одном контексте, сложились после расширения опыта. Именно потому, что сон повторил **не то, что известно**, а то, что **осталось непонятым**.

## Активное внимание: куда движется система

На всех описанных этапах система была **реактивной**: учитель подавал тексты, система их обрабатывала. Это правильное начало — нужно сначала убедиться, что механизм обучения работает. Но это не цель.

**Цель** — система, которая сама формирует программу вопросов к миру:

```
Сейчас (реактивная):
  Учитель → driver.produce(text) → токены → engine.step() → Gen

Цель (активная):
  Контекст → InitiativeEngine.propose() → запрос к драйверу → токен → step() → (цикл)
```

`InitiativeEngine` уже реализован и уже генерирует `Proposal(gen_id, next_feature_id, confidence)` — это «ожидание», которое система хотела бы проверить. Но пока это ожидание **не выполняется как команда**: нет компонента, который бы переводил «ожидаю feature X» в «попроси драйвер показать X».

Это следующий принципиальный шаг. Данные не должны загружаться принудительно. Система должна сама **формировать минимальную программу вопросов к периферии**.

## Временна́я архитектура: нырки

Ещё одно важное открытие, которое проявилось в экспериментах: Gen живут в **разных временны́х масштабах**.

```
ДОЛГОСРОЧНЫЕ  (chain=1–2, significance≈1.0)
  "Я нахожусь в лесу"
  "Сейчас Пух ищет мёд"
  Меняются редко. Активны почти всегда. Задают фильтр восприятия.

СРЕДНЕСРОЧНЫЕ (chain=3–4, significance=0.7–0.9)
  "Пух идёт к дубу"
  "Пятачок рядом"
  Текущая ситуация. Обновляются по ходу события.

ОПЕРАТИВНЫЕ  (chain=5+, significance=0.4–0.7)
  "Следующее слово будет 'мёд'"
  "Этот переход ведёт к глаголу"
  Момент-к-моменту. Создаются быстро, быстро устаревают.
```

Система **«ныряет»** из долгосрочного контекста в оперативный и обратно. Долгосрочные Gen задают гипотезу о мире («я в лесу»), оперативные её уточняют («ветка справа»). При сильном расхождении (REFUTED на нескольких уровнях) — «всплытие» и пересмотр долгосрочной гипотезы.

TimescaleScheduler реализует эти три пула явно и управляет тем, какие Gen «выталкиваются» при переполнении CapacityBudget — в первую очередь вытесняются оперативные с низкой витальностью.

## Что значит «понять» для этой системы

В конце хочется сформулировать, что же происходит, когда система «понимает» текст.

Это не извлечение семантики. Не классификация. Не предсказание следующего токена в привычном смысле.

**Понять** для этой системы — значит, что:
1. Ожидание сформировалось из прошлого опыта (active Gen в контексте)
2. Реальность его подтвердила (CONFIRMED / COMPLETED)
3. Значимость выросла

**Удивиться** — значит, что:
1. Было ожидание
2. Реальность его опровергла (REFUTED)
3. Создано новое обобщение — «мир оказался богаче»

**Забыть** — значит, что urgency Gen вышла за порог, а витальность упала до нуля. Система перестала «слышать» этот голос.

**Приснилось** — значит, что непонятое днём было воспроизведено ночью в расширенном контексте и стало понятным. Мета-Gen с доменами [лес, горы] как отпечаток этого инсайта.
