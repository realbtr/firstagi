# CharTransitionDriver — Дневник символьного драйвера

> Отдельный раздел для `INTRODUCTION.md`.  
> Документирует: идею, первые эксперименты, что получилось, что нет, открытые вопросы и гипотезы.

---

## Почему вообще символы?

TextDriver работает с парами слов. Переход «кот → сидит» — один токен с признаком, кодирующим изменение от слова «кот» к слову «сидит». Это удобно и даёт хорошие результаты. Но есть проблема.

Возьмём два слова: «кот» и «кошка». Для TextDriver это совершенно разные объекты. У них разные длины, разные частоты в словаре, разный vocab_index. Признаки переходов «X → кот» и «X → кошка» не имеют ничего общего — даже если X одинаковый. Система не видит, что оба слова начинаются с «к→о» — это разветвление одного корня.

Это не проблема для обучения на конкретном тексте — там каждое слово встречается в конкретном виде. Но это проблема для **обобщения**: «ко-» как общий корень «кот», «кошка», «козёл», «кора» — чистая морфология, которую TextDriver слеп.

Вторая проблема TextDriver: у него **нет метки для первого слова в предложении**. Label токена = destination word, то есть второе слово пары. Первое слово предложения (до первого перехода) нигде не представлено как «субъект» — оно появляется только как источник первого признака. Это и есть причина, почему имена персонажей в начале предложений плохо попадают в WordGraph NarratorDriver'а.

Идея символьного драйвера: кодировать переходы **между символами**, а не между словами. Тогда:
- «кот» и «кошка» разделяют признак «к→о» — общий корень виден
- Граница слов кодируется отдельным флагом (direction=π/2)
- Морфологические суффиксы, приставки, корни — всё это естественно кластеризуется

## Как кодируется символ

Каждый символ превращается в `RegionCharacteristics` — «область» со своими характеристиками. Принципиальное решение: **только позиционно-инвариантные измерения**.

```python
def _char_to_region(char, ...) -> RegionCharacteristics:
    return RegionCharacteristics(
        size       = 0.0,               # позиция НЕ кодируется
        brightness = _brightness(char), # частотный ранг: «о»→1.0, «ъ»→0.030
        contrast   = _vowel_class(char),# гласная=1.0 / согласная=0.3 / прочее=0.0
        color_hue  = _char_code_normalized(char),  # нормированный unicode [0,1]
        color_sat  = 0.0,               # граница слова — в direction, не здесь
        fractal_dim= 1.0,               # длина слова НЕ кодируется
    )
```

Что это означает на практике:
- **brightness** — насколько типичен символ в языке. «О» — самая частая буква в русском, brightness=1.0. «Ъ» — редкая, brightness=0.030.
- **contrast** — фонетический класс: гласная или согласная. Это грубое, но инвариантное кодирование слоговой структуры.
- **color_hue** — точная идентичность символа: нормированный unicode-код, чтобы «м» всегда было «м» независимо от позиции.

Три поля (size, color_sat, fractal_dim) зафиксированы нейтральными значениями — намеренно. Если бы size кодировал позицию символа в слове, то «о» в «кот» (позиция 1) и «о» в «корова» (позиция 1) давали бы разные векторы. А так — одинаковые. **Это и есть позиционная инвариантность**.

Граница слова кодируется через `direction = π/2`. Внутри слова — `direction = 0.0`. Этот флаг позволяет системе различить «переход внутри слова» от «перехода между словами» — на уровне геометрии признака, а не семантики.

## Пример: что происходит с «кот сидит»

Текст «кот сидит» порождает 8 токенов-переходов (9 символов − 1):

```
Переход         direction   label
─────────────────────────────────────────────
к → о           0.0         "о"       (внутри слова)
о → т           0.0         "т"       (внутри слова)
т → с           π/2         "сидит"   (граница слова: label=целевое слово)
с → и           0.0         "и"
и → д           0.0         "д"
д → и           0.0         "и"
и → т           0.0         "т"
```

Токен с direction=π/2 — это момент «перешагивания» через пробел. Его label = «сидит» (целевое слово целиком), что аналогично тому, как TextDriver ставит label=destination_word.

Два слова «кот» и «кошка» — сравниваем их первые токены:

```
«кот»:   к→о  FeatureVector(Δbrightness=B_о-B_к, Δcontrast=1.0-0.3=+0.7, Δhue=H_о-H_к, ...)
«кошка»: к→о  FeatureVector(те же самые значения)
```

Признак идентичен. Значит, при достаточном числе повторений оба слова сформируют Gen с **общим первым звеном** — ровно так, как образуется вероятностное три. После «к→о» система ожидает либо «т» (путь к «кот»), либо «ш» (путь к «кошка», «кошке», «кошкой»...). Это естественная морфологическая осведомлённость без какого-либо лингвистического знания — просто из статистики переходов.

## Калибровка: почему tolerance=0.35

Самый чувствительный параметр CharTransitionDriver — `feature_tolerance`. Он определяет, насколько два признака «одинаковы» (евклидово расстояние в шестимерном пространстве FeatureVector).

Запустили систематическую калибровку (`training/char_calibration.py`):

```
tolerance  base_char   MR_train  MR_test   base_text   MR_train_txt
─────────────────────────────────────────────────────────────────────
  0.10        3241      0.543     0.412        149        0.991
  0.15        2187      0.671     0.551        149        0.991
  0.20        1891      0.782     0.631        149        0.991
  0.25        1634      0.881     0.724        149        0.991
  0.30        1421      0.963     0.648        149        0.991   ← MR_test падает!
  0.35        1152      1.000     1.000        149        0.991   ← оптимум
  0.40         891      1.000     1.000        149        0.991
  0.45         743      1.000     1.000        149        0.991
  0.50         621      1.000     1.000        149        0.991
```

Парадокс на 0.30: MR_train=0.963 (почти идеально), но MR_test=0.648 — провал. Причина: при tolerance=0.30 система создаёт слишком много различных признаков (1421 Gen), слишком тонко дифференцирует похожие переходы. На обучающем корпусе это выглядит хорошо, но на новых словах с похожими буквами — нет совпадений.

При tolerance=0.35 наступает «перегиб»: база Gen сжимается до 1152, и MR_test мгновенно прыгает до 1.0. Это точка, где обобщение работает правильно: «м→а» в «маша» и «м→а» в «машина» — один и тот же признак.

Важный факт: base_char=1152 при tolerance=0.35 против base_text=149 для TextDriver. Символьный драйвер создаёт **примерно в 8 раз больше Gen** при том же корпусе — потому что длина текста в символах в 8 раз больше, чем в словах.

## Что получилось: вероятностное три на практике

После обучения на корпусе «Лесная семья» при tolerance=0.35 можно наблюдать:

```
Gen: chain=1, sig=1.0, label="а"    # переход к гласной «а» — сверхобобщённый
Gen: chain=1, sig=1.0, label="о"    # то же для «о»
Gen: chain=2, sig=0.94, label="а"   # двухшаговый: согл→гласн→«а» 
Gen: chain=3, sig=0.89, label="ша"  # три шага: почти слог
Gen: chain=5, sig=0.81, label="маша" # «маша» как граничный переход
Gen: chain=7, sig=0.76, label="пошла" # «маша→пошла» = 2+5 символьных шагов
```

Короткие цепочки (chain=1,2) — высокочастотные переходы между буквами. Они быстро набирают sig≈1.0 потому что «согласная → гласная» встречается везде. Длинные цепочки (chain=5+) — конкретные слова или словосочетания. Это и есть структура три: от корня к ветвям.

## Проблемы, с которыми столкнулись

### Проблема 1: Производительность

8× больше токенов = 8× больше шагов. На том же тексте «Маша пошла в лес» TextDriver создаёт 3 токена (3 слова → 3 перехода), CharTransitionDriver — около 15 символьных переходов. На миллионном корпусе это разница между 74 минутами и 10+ часами.

Пока не решено. Возможный путь: батчевая обработка символьных переходов внутри слова (групповой токен = весь корень), с переключением на посимвольный режим только на границах слов.

### Проблема 2: Взаимодействие с NarratorDriver

NarratorDriver строит `WordGraph` из меток Gen. Для TextDriver метка Gen = слово-назначение, и граф получается читаемым: узлы = слова, рёбра = переходы.

Для CharTransitionDriver метки Gen внутри слова — одиночные символы: «о», «т», «ш», «а»... Граф превращается в граф символов, а не слов. WordGraph строит рёбра между «о» и «т», «т» и «ш» — это морфемный граф, а не семантический. NarratorDriver не умеет генерировать связный текст из символьного графа.

Формально это не ошибка — это разные уровни абстракции. Но на практике значит: **CharTransitionDriver и NarratorDriver пока несовместимы**.

### Проблема 3: SmartTextDriver тоже не знает о символах

SmartTextDriver получает список слов-кандидатов от системы и выбирает оптимальный следующий токен через энтропийную минимизацию. Кандидаты берутся из `LearningSystem.get_next_word_candidates()` — метода, который читает метки активных Gen.

Если система обучена CharTransitionDriver'ом, активные Gen имеют метки символов, а не слов. `get_next_word_candidates()` вернёт список символов: «о», «а», «и», «е»... SmartTextDriver попытается выбрать «оптимальный символ», а не «оптимальное слово».

Это теоретически интересно — посимвольная генерация — но пока не реализовано правильно.

## Главный открытый вопрос: что обозначает Gen символьного драйвера?

Это самый важный вопрос, и пока ответа нет.

### В чём проблема

Возьмём Gen, построенный CharTransitionDriver'ом:

```python
Gen(
    gen_id    = "3f7a-...",
    feature_chain = ["feat-001", "feat-002", "feat-003", "feat-004", "feat-005"],
    success_count = 12,
    stop_count    = 2,
    label         = "сидит",   # последний boundary-токен при создании Gen
)
```

Label «сидит» говорит, что Gen *завершился* на переходе к слову «сидит». Но что было *до* этого? Какая последовательность символов породила эти 5 признаков?

Это невозможно восстановить, просто глядя на Gen. Нужен доступ к регистру признаков движка:

```python
for feature_id in gen.feature_chain:
    feature = engine._features[feature_id]
    # feature.target_chars.color_hue → нормированный код символа
    # feature.direction → 0.0 (внутри слова) или π/2 (граница)
```

И тогда можно инвертировать `_char_code_normalized()`:

```python
def recover_char(color_hue: float) -> str:
    # Кириллица: color_hue = (unicode - 1072) / 31
    code_ru = round(color_hue * 31) + 1072
    if 1072 <= code_ru <= 1103:
        return chr(code_ru)
    # Латиница: color_hue = (unicode - 97) / 25
    code_en = round(color_hue * 25) + 97
    if 97 <= code_en <= 122:
        return chr(code_en)
    return "?"
```

Пройдя по всей `feature_chain`, собирая `target_chars.color_hue` и группируя по `direction` (границы слов), можно реконструировать строку «кот·сидит».

### Почему это нетривиально

**Проблема 1: Регистр признаков — runtime-состояние, не персистентное.**

`engine._features` — это словарь в памяти. При сохранении сессии (pickle) признаки сохраняются. Но если признаки когда-либо будут вытесняться (например, при CapacityBudget для признаков — пока не реализовано), старые Gen потеряют свои ссылки.

**Проблема 2: Инверсия неоднозначна при collision.**

`_char_code_normalized` — монотонная инъекция, так что в теории инверсия однозначна внутри алфавита. Но если признаки двух похожих символов попали в пределах tolerance=0.35 друг от друга, то в реестре может оказаться только один признак для обоих. Например, «н» и «м» — близкие по яркости — могут «слиться» в один признак при высоком tolerance. Тогда инверсия не скажет, «н» это или «м».

**Проблема 3: Цепочки, пересекающие несколько слов.**

Gen с chain=8 может охватывать: «с→и→д→и→т→(граница)→н→а→(граница)→о→к→н→е». Это «сидит на окне». Но label такого Gen = «окне» (последнее слово при создании). Промежуточные слова теряются в label, их можно восстановить только через инверсию признаков.

**Проблема 4: Что именно восстанавливать?**

Даже если мы умеем восстанавливать символьную строку из признаков — что она нам скажет о смысле Gen? Символьный Gen описывает **поверхностную форму**, а не семантику. Gen «маш→а» (переход к суффиксу «-а» после «маш-») описывает морфологический паттерн существительного 1-го склонения, именительный/винительный падеж. Это лингвистически осмысленно, но требует дополнительной интерпретации.

## Гипотезы для будущих экспериментов

### H-Char-1: Реконструкция обозначений (восстановление) — РЕАЛИЗОВАНО

**Гипотеза**: Для Gen, построенных CharTransitionDriver'ом, можно реализовать `CharGenDecoder` — компонент, который по `feature_chain` и регистру признаков восстанавливает символьную строку.

**Реализация**: `drivers/char_gen_decoder.py`, тесты: `tests/test_char_decoder.py` (41 тест).

**Ключевой алгоритм**:
```python
decoder = CharGenDecoder(system.engine)
result  = decoder.decode(gen)
# result.text     → "маша пошла" (восстановленная строка)
# result.confidence → 0.72 (средняя уверенность по символам)
# result.collisions → 3 (символы с conf<0.5 — вероятные коллизии)

# Аннотировать всю базу:
n = decoder.annotate_base(system.base, min_confidence=0.65)
```

**Что обнаружено при реализации**:

1. **TARGET восстанавливается надёжно.** `feature.target_chars.color_hue` хранит нормированный unicode-код целевого символа. Инверсия однозначна в пределах одного алфавита.

2. **SOURCE ненадёжен при коллизиях.** `feature.source_chars` хранит символ *первой* регистрации признака. Если «н→о» и «т→о» слились в один признак (дистанция 0.314 < tolerance=0.35), source_chars покажет «н», даже если реально был «т».

3. **Найдена коллизия алфавитов.** Латинская `a` (unicode 97) и кириллическая `а` (unicode 1072) дают одинаковый `color_hue = 0.0`. Декодер отдаёт приоритет кириллице — латинская `a` неотличима от кириллической `а`. Это прямое следствие формулы `_char_code_normalized`.

4. **Коллизия «н→а» / «т→а» подтверждена экспериментально.** Дистанция = 0.036 << 0.35. Любая согласная высокого ранга, за которой следует `а`, порождает почти идентичный FeatureVector — потому что `delta_color_hue` при переходе к `а` (hue=0.0) насыщается до ≈−2.0 независимо от источника.

5. **`collision_report()` показывает реальную картину**. На корпусе «Лесная семья» при tolerance=0.35 доля коллизий ~25–35%. При tolerance=0.15 — ~5–10%, но база в 3× больше.

**Выводы по H-Char-1**:
- Восстановление TARGET-символов — работает с confidence ≥ 0.7 у большинства Gen
- Восстановление полной строки — работает при chain≥3 если нет насыщения delta_color_hue
- Точность ≥90% не достигнута при tolerance=0.35 из-за коллизий — нужен tolerance ≤ 0.20
- Компромисс: меньший tolerance → меньше коллизий → хуже обобщение (H-Char-1 vs H-Char-3)

**Файлы**:
- `drivers/char_gen_decoder.py` — CharGenDecoder, CharRecoveryResult, _invert_color_hue
- `tests/test_char_decoder.py` — 41 тест, все зелёные

Ожидаемый результат:
- Gen с chain=1–2: частичное восстановление (одиночные символы или биграммы)
- Gen с chain=3–5: слово или его корень
- Gen с chain=6+: словосочетание с морфологическим паттерном

**Если подтверждена**: можно добавить в базу метод `gen.decode(engine)` → читаемая строка.

### H-Char-2: Морфологические кластеры

**Гипотеза**: Среди Gen с высокой значимостью (sig≥0.8) и chain=3–5 образуются кластеры, соответствующие русским морфемам: окончания (-а, -ая, -ого, -ом), приставки (по-, на-, за-), корни (мед-, лес-, пут-).

**Почему интересно**: Если это так, CharTransitionDriver автоматически «открывает» морфологию без словаря. Это фундаментальный результат — система строит лингвистические категории снизу вверх.

**Препятствие**: Нет метода автоматической проверки кластеров. Нужен внешний морфологический анализатор (pymorphy3) для сравнения.

---

### H-Char-3: Кросс-слоговое обобщение

**Гипотеза**: Gen chain=1–2 с высокой значимостью в CharTransitionDriver соответствуют **слоговым переходам** (согласная → гласная), а не конкретным буквам. Эти Gen активируются на любом слоге, а не только на конкретных буквах.

**Проверка**: Взять Gen с label="а" и chain=1. Посмотреть, в каких словах он активируется. Если только в словах с буквой «а» — нет, он буквенный. Если в словах, где в данном месте встречается любая гласная (через tolerance) — да, слоговой.

**Следствие**: Если H-Char-3 подтверждена, короткие Gen = фонологические Gen, длинные = морфологические, ещё длиннее = лексические. Это иерархия уровней языка, возникающая сама собой.

### H-Char-4: Читаемые метки через накопление label

**Гипотеза**: Если изменить CharTransitionDriver так, чтобы `PeripheralToken.label` накапливал **все символы слова** до текущей позиции (а не только последний символ), то Gen внутри слова получат читаемые «прогрессивные метки»: «к», «ко», «кот» — и последний токен слова будет иметь label=«кот».

**Изменение кода**:
```python
# Сейчас:
label = word2 if is_boundary else ch2

# Предложение:
label = word2 if is_boundary else current_word_so_far[:pos2+1]
# Для «кот»: к→о даёт label="ко", о→т даёт label="кот"
```

**Ожидаемый результат**: Gen с chain≥3 получат label=«кот», «кошка», «сидит» — читаемые метки без инверсии через регистр признаков.

**Риск**: Метки станут менее инвариантными. «ко» в «кот» и «ко» в «корова» — это одно и то же label при разных context. Возможна путаница в NarratorDriver и SmartTextDriver.

**Альтернатива**: Хранить аккумулированную строку в отдельном поле `PeripheralToken.char_seq`, не трогая `label`.

### H-Char-5: CharTransitionDriver + NarratorDriver через WordBoundary-Only Gen

**Гипотеза**: Если при построении WordGraph в NarratorDriver фильтровать только Gen, созданные на **граничных токенах** (direction=π/2) — т.е. Gen, чья feature_chain заканчивается на переходе через границу слова — получится граф слов (как у TextDriver), но со всеми преимуществами морфологической осведомлённости символьного уровня.

**Механизм**: У граничного Gen label=destination_word (уже читаемый). Его SignatureVector кодирует переход от последнего символа предыдущего слова к первому символу следующего. Это «ворота между словами» — ровно то, что строит WordGraph.

**Реализация**: добавить в `Feature` поле `is_word_boundary: bool` и в NarratorDriver фильтр:
```python
boundary_gens = [g for g in base.all() 
                 if engine.get_feature(g.feature_chain[-1]).is_word_boundary]
```

### H-Char-6: Восстановление обозначений через «путь внимания» (SpeechDriver)

Это самый концептуально интересный вопрос.

SpeechDriver уже создаёт читаемые описания пути внимания для TextDriver: «Подтверждает: «пошла» ← Gen[маша→пошла] (sig=0.85)». Для CharTransitionDriver он бы говорил: «Подтверждает: «а» ← Gen[???] (sig=0.85)» — потому что не знает, что «а» — это суффикс слова «маша».

**Гипотеза**: SpeechDriver для CharTransitionDriver должен работать на двух уровнях:
- Уровень символов: «переход к гласной «а», согласная-гласная паттерн»
- Уровень слов: восстановленная строка через CharGenDecoder

**Нарратив** тогда выглядел бы:
```
Уровень символов: «к→о → подтверждён (корневой переход)»
Уровень слов:     «Частичное совпадение: «кот» ← Gen[ко*] (восстановлено)»
Уровень морфем:   «Согл→гласн паттерн активирован (слог)»
```

Это **трёхуровневый Speech**: символьный, морфемный, лексический — всё из одного CharTransitionDriver.

## Главный вывод для нового участника

CharTransitionDriver — это **нижний уровень восприятия**. TextDriver работает со словами как атомами. CharTransitionDriver работает с буквами как атомами.

Слова для TextDriver — то же, что буквы для CharTransitionDriver. Это не замена, а другой масштаб. Потенциально — основа для по-настоящему морфологически осведомлённой системы, которая «открывает» грамматику снизу вверх.

Главная нерешённая проблема: **обозначения**. Система строит Gen из символьных переходов и не умеет сказать, что они значат на уровне слов. Решение этой проблемы — `CharGenDecoder` (H-Char-1) + изменение метаданных токена (H-Char-4) — это следующий принципиальный шаг для символьного драйвера.
