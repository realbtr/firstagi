# V3: расчёт допуска connecting Gen до протокола AC0-T

**Статус: черновой логический расчёт, не запуск learner и не протокол.**
Основание: REVIEW_2026-11-02_pr33.md, V2/V3/V6/V8.
Архитектура: [T3/G1](T3_GENERALIZED_OPERATION_KEYS_v0_2.md).
Schedule ниже — предложение для проверки возможности допуска; ревьюер ещё
не принял его как curriculum. Manifest, seeds и confirming не открываются.

## Допущения и счётчики

Пример одной O, затем тот же заранее заданный блок для каждой O меню.
Публичная схема: роль C4, непрозрачная O, опора x, местность t и посторонний n.
Все x различны; role/O постоянны. G — наблюдённое относительное продолжение
от замороженного x; для расчёта значения +1/-1 — метки двух разных классов,
не подсказка ядру об эффекте O. Его O→G извлекается только из actual.
Наблюдения в curriculum полные; ни цель, ни split train/closed не входят в K.
Ключи строятся по всем публичным признакам, маска релевантности не дана.
Сильной таблице разрешение t дано явно; полный контроль хранит весь контекст.

Обозначения: o — единственный origin, pf — число последующих положительных
замороженных прогнозов, nneg — отрицательные. В этом расчёте допуск требует
o=1, pf≥2, p/(p+nneg)>0.5 и остальных A3/availability условий.
Это консервативно: не считать origin одним из двух прогнозов V3. При хранении
legacy p с origin условие pf проверяется отдельно, без ослабления старого A1.
Два события пары создания дают один origin (первое), второе расходуется
только на создание K. Событие расширения — origin нового connecting Gen,
не positive. Прогнозы начинаются строго со следующего actual.

Индекс консолидации в расчёте рассматривает все совместимые K этого малого
блока; если manifest ограничивает поиск раньше, расчёт неприменим и NOT_READY.
Перебор полный по всей базе не предполагается. Ни расширение, ни уточнение
не наследует p/n. Все arms получают одинаковые операции, receipts и schedule.

## Однородный блок: пять actual на O

t=a всегда, G=+1; x меняется на каждом шаге.

| Actual | n | Состояние после actual | o / pf / nneg нужного носителя |
|---|---|---|---|
| 1 | 0 | Непарное исполнение | — |
| 2 | 0 | K0: t=a,n=0; x переменная; создан connecting0 | 1/0/0 |
| 3 | 1 | K0 reject; расширение K1: t=a,n=?n; connecting1 | 1/0/0 |
| 4 | 2 | K1 match; первый frozen forecast совпал | 1/1/0 |
| 5 | 3 | K1 match; второй frozen forecast совпал, допуск | 1/2/0 |

K1 достаточно общий для новых x и n, но не переносится на невиданную t.
Поэтому однородный closed сохраняет t=a; это явная граница проверки.
Closed меняет n на ранее не встречавшиеся значения и x на новые опоры.
Следующий n не создаёт редакцию K1: переменная уже распознаёт его.
Узкий connecting0 совместим по G, но его evidence не прибавляется к connecting1.

## Неоднородный блок: десять actual на O

Для примера O имеет G=+1 при t=a, G=-1 при t=b. n причинно не влияет.
Блок a повторяет строки1–5 выше. Блок b:

| Actual | t,n | Состояние после actual | o / pf / nneg |
|---|---|---|---|
| 6 | b,0 | K(a) reject; непарное исполнение для G=-1 | — |
| 7 | b,0 | Kb0: t=b,n=0; новый connecting | 1/0/0 |
| 8 | b,1 | Kb0 reject; расширение Kb1: t=b,n=?n | 1/0/0 |
| 9 | b,2 | Первый frozen forecast Kb1 | 1/1/0 |
| 10 | b,3 | Второй frozen forecast Kb1; допуск | 1/2/0 |

K(a) допускается после actual5, K(b) после actual10. Разные G не объединяются
в один ключ. Этот schedule проверяет создание/расширение; конфликтное
уточнение и G1 требуют отдельных acceptance cases и curriculum в протоколе.
В частности, он не доказывает способность обнаружить скрытый разделитель.
Неоднородный closed содержит новые x/n, но обе обученные t. Перенос на новую
причинно значимую t не предсказывается. Любой другой O использует отдельные
наблюдаемые actual, общие evidence между O не заимствуются.

## Вывод R1 и бюджет до протокола

При этих допущениях допуск возможен: 5 actual/O для однородного случая,
10 actual/O для двух местностей. Для m операций — 5m и 10m соответственно.
Это нижняя проверяемая заявка на curriculum, а не эмпирическая гарантия.
Протокол не может назначить меньший бюджет и оставить тот же прогноз R1.
Лимит менее5/10 actual на O или неполное покрытие индекса даёт NOT_READY;
ослаблять pf≥2 запрещено. При реальном отставании K/новых редакциях после
этих шагов фиксируется отказ допуска в бюджете, без продления серии.

Сравниваются отдельно: exact/native без общего K; полная контекстная таблица;
сильная таблица с заданным разрешением t; native K; no-Q/random-Q/G1 в
отдельной части с частично доступным t. Все получают одинаковый schedule.
Полная таблица на новых x/n не знает полный контекст. Сильная таблица может
достичь паритета точности; это допустимо. До данных протокол фиксирует
число actual до допуска, байты состояния и цену проверок, а также общие
лимиты сравнений/памяти/чтений. Численных acceptance thresholds здесь нет.

Перед принятием протокола нужны: точная публичная кодировка и домены,
порядок пар/расширений, стоимость поиска, acceptance cases уточнения/G1,
численные бюджеты и план измерения V8. Этот расчёт снимает только риск
невозможности допуска на приведённом schedule, не остальные основания NOT_READY.
