## 2. Где проходит граница ядра и драйвера

Драйвер сообщает наблюдение, доступные **адреса команд** и желаемое публичное
различение; выполняет ровно выбранный адрес и возвращает actual receipt.
Он не ранжирует команды, не раскрывает Gen, не сравнивает прогноз с целью,
не хранит таблицу последнего исхода для выбора и не знает hidden slot/mapping.

Внутри LearningSystem живут актуальная цель, применимость Gen, конкуренция,
проверка actual и её происхождение. Цель — ограничение текущей траектории,
не наблюдённый факт: её предъявление не подтверждает знание или исход.
Один и тот же алгоритм обслуживает любой драйвер этого контракта; никаких
ветвей по torus, номеру канала, имени экземпляра, тексту метки или LLM.

Используем понятия ONTOLOGY: Gen, актуальный контекст, предложение, команда
перехода внимания, внешний исход и evidence. Предлагаемые API ниже ещё
не существуют. Будущие поля/семантику provenance сначала отразить в ONTOLOGY.

## 3. Ограниченный вариант: конкуренция подтверждённых продолжений

### 3.1. Обученная связь, а не новая таблица ответов

Предлагается использовать `key_id/oper_id/goal_id` **существующего Gen** как
ссылки на распознанные ядром опору, команду и наблюдённое продолжение.
`goal_id` этой выученной связи означает предсказанное следствие, а текущая
желаемая цель хранится отдельно в контексте. Совпадение двух ролей не задано.

Связи заполняет learner только после настоящей последовательности
наблюдение → исполненная команда → доставленный actual и появления
соответствующей native цепи. Оpaque operation ID служит адресом, не ответом.
Не создавать такой Gen или его ссылки из правильного evaluator label,
из желаемой цели, из будущего outcome или вручную из training answer table.
Принудительная curriculum-команда допускается с явной отметкой и не считается
инициативой ядра; утверждение о native действии начинается на поздней пробе.

В Gen хранится provenance фактических receipt IDs/ссылок на наблюдения для
этой связи. Это не отдельный решатель `(cue,operation)->answer` в адаптере.
Если связь не восстановлена из native цепи или origin неоднозначен —
предложение недопустимо. Тест должен получать связь через learner, а не
только показывать работоспособность вручную заполненных полей.

### 3.2. Поддержка по исходам требует отдельной семантики

Не выдавать текущие `success_count/stop_count` за число проверенных действий:
они уже меняются при сопоставлении промежуточных признаков. Их прежнюю
семантику и текстовый pipeline в этом варианте сохраняем.

Для командного продолжения предлагается **provenance по actual внутри того
же Gen**: положительные/отрицательные квитанции прогноза и учёт дедупликации.
Оценка поддержки выводится из них, без дублирующей таблицы выбора команды.
Новый числитель/знаменатель — positive/(positive+negative); без наблюдённых
исходов Gen не допускается к подтверждённому native выбору. Unknown ничего
не прибавляет. Объём квитанций, индексов и кэшей входит в общую память.

Положительность определяется совпадением **предсказанного** и actual,
а не достижением текущей цели. Верный прогноз неуспеха задачи может иметь
positive evidence; task success считает независимый evaluator.
Не переносить старые token counters в actual evidence без квитанций.
Это предлагаемое расширение данных Gen, требующее отдельного одобрения:
если оно меняет основную теорию поддержки, ревьюер останавливает реализацию.

### 3.3. Актуальный путь до команды

Предлагаемые интеграционные точки, без новой внешней управляющей модели:

1. `LearningSystem.propose_operations(public_view)` получает текущую цель
   и легальные адреса, обрабатывает cue существующим core path и восстанавливает
   применимые длинные Gen в **живой**, а не временно собранный внешний контекст.
   Расширение загрузки выполняется внутри AttractorEngine; prefix scan имеет
   счётчик посещений/предел. Пустое восстановление означает wait/abstain.
2. Из `ContextBuffer.get_expected_features` берутся **все** применимые
   продолжения с проверенной native связью. До top3/группировки проверяются
   позиции, роли, channel/source, доступность команды, provenance и цепь
   прогнозируемого следствия. Чужой канал не даёт подтверждение этому каналу.
3. В ядре желаемое различение сопоставляется с выученным следствием через
   согласованный Feature/Gen контракт. Оpaque ID может подтверждать идентичность,
   но не подменяет отношение сходства. Кодирование одинаково для actual и
   целевого различения и фиксируется в manifest **до development**.
4. Конфликтующие живые прогнозы одной команды проверяются полностью.
   Если один Gen обещает цель, другой достаточный Gen той же команды — иной
   исход, confidence/top3 не скрывают конфликт: команда отмечается ambiguous.
5. Сначала goal-compatible и непротиворечивые команды, затем конкуренция
   в InitiativeEngine: поддержка по actual × существующий novelty factor.
   Порядок меню/UUID/label не решает когнитивную ничью. При равенстве без
   установленного различия — abstain; внешний random fallback маркируется
   и не получает заслугу полезного Gen. Формула/допуск фиксируются до данных.
6. Свежий Proposal содержит выбранный адрес, **всех** contributors и позиции,
   ссылки на прогнозы/evidence, driver/channel, base/context version и seq.
   Его создаёт текущий core вызов после cue; прошлый `last_proposals` не подходит.
7. Драйвер проверяет только целостность/свежесть адреса и исполняет его.
   Он не выбирает запасной вариант при stale/ambiguous/no-evidence.

Это не rename `select_goal`: требуются native обучение связи, реальный
context recall, применимость до конкуренции, полный состав прогнозов,
жизненный цикл команды и actual evidence. Перенос старого selector в core
без этих различий не считается реализацией дизайна.

## 4. Фактический исход и локальное продолжение

Предлагаемый `LearningSystem.accept_operation_outcome(...)` связывает
receipt с ожидающей командой и её зафиксированными прогнозами. Проверяются
instance/channel/seq/operation и уникальный receipt ID. Факт исполнения и
факт наблюдения различаются; повтор доставки не становится новым опытом.

На observed actual ядро обновляет evidence всех относящихся к исполненной
команде прогнозов из зафиксированного состава конкуренции, а не только
удобного победителя. Дальше снова сопоставляет актуальные условия.
Generic token ingestion остаётся источником native learning, но его
CONFIRMED/REFUTED не дублирует actual receipt counters.
Unknown/unavailable сохраняет pending и не даёт negative evidence;
interruption временно снимает доступность продолжения. Поздний actual
принимается только к своей ещё допустимой pending-команде один раз.
Политику отмены/истечения pending закрепить до реализации, без выдуманного
таймера или отрицания при отсутствии наблюдения.

## 5. Причинный носитель и intervention hook

Носитель — допустимость **конкретного Gen** в актуальном контексте и всех
путях, которые раскрывают его для текущей командной конкуренции.
Предлагается общий core predicate применимости, используемый при загрузке,
чтении ожиданий, раскрытии ссылок и финальной проверке Proposal.
В ordinary режиме он сохраняет обычную доступность; в зарегистрированном
causal опыте временно запрещает target Gen для этой пробы.

Удалить target из active context недостаточно: последующий recall не должен
вернуть его. Фильтр после ранжирования недостаточен: target мог уже изменить
конкуренцию. При этом base/features/evidence не стираются, scalar significance
не обнуляется, другие каналы и достаточные Gen остаются доступными.
Независимо закодированное продолжение родителя — альтернативное условие,
его нельзя молча заблокировать ради красивой необходимости одного Gen.

Идентичные checkpoint/input/random variates: available → sham → blocked →
restored. Записать обращения к носителю, полный список альтернатив, действие
и последующий контекст. Stale proposal проверяется после изменения условия
ещё раз. Если другой достаточный Gen сохраняет действие — redundancy,
не доказанная single-Gen necessity. Восстановление доступности не учит заново.

## 8. Решение, которое требуется от ревьюера

Принять/изменить: (1) обучение key/operation/outcome связи внутри Gen,
(2) evidence по actual отдельно от старых token counters, (3) цель и полная
конкуренция внутри core до усечения, (4) общий causal applicability guard.
Особенно проверить, не превращается ли расширение evidence/ролей в новую
архитектуру и не переносит ли драйвер существенную часть решения.

После принятия — отдельный implementation PR с тестами и конкретным encoding,
затем manifest, один development на60101/60102 и техническое ретро до
confirming90101–90108. До принятия дизайна все эти шаги остаются закрыты.
Перенос на невстречавшиеся cue/operation сочетания и полезность12-звенной
цепи этим source audit не установлены; компактность не является gate.
