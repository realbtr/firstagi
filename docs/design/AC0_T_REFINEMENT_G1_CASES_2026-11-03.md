## 1. Концепция и проверяемое различие

T3 связывает род условия с родом продолжения. Рабочая гипотеза H-T —
условие огрубляется при совпадении последствий и уточняется при расхождении.
G1 — выбор того, какое различение проверить до действия. Здесь проверяется
контракт будущего уточнения и чтения, а не правдоподобность рассказа о них.

Проверяемая причинная цепь: распознанное K → замороженный прогноз C/G →
операция → actual → пересмотр допуска/условия → следующее предложение.
Снятие K или C проверяется отдельно от изменения числа p/n. Новый носитель
не получает подтверждения старого; чтение признака не становится actual
внешнего действия. Цель G* не создаёт evidence.

## 2. Условная fixture для уточнения

Одна непрозрачная O, публичные x, t и n. `t` имеет домен {a,b,c},
`n` — посторонний признак; x/n варьируются. Относительные G+ и G− различимы
детерминированным evaluator относительно замороженного x. Их численная
кодировка будет в протоколе; обозначения не сообщаются learner как ответы O.

Среда стационарна: одна O даёт G+ при t=a/b и G− при t=c. Learner получает
эту связь только через actual. Предлагаемый условный curriculum: actual1
с (a,n0), actual2 с (b,n1), actual3 с (a,n2), все с различными x и G+.
Второй actual создаёт C0 с широким K0=(t=?t,n=?n,x=?x) и одним origin;
третий имеет frozen G+ и даёт pf=1. Channel/роль/O также входят в K.
Это развитие создания/обобщения из принятого дизайна, не измеренное
поведение learner. Возможность такого построения должна быть проверена
будущим компонентным тестом; если K0 не получен, зафиксировать отказ
построения, не подложить его в исследовательский запуск.

На actual4, впервые с t=c и новым x/n, до dispatch заморожен G+, но приходит
G−. Наблюдённый разделитель t=c отделяет этот исход от обоих прежних типов
t=a/b. Скрытой перемены закона среды и противоречия для одного и того же t
нет. Новый домен из трёх значений предложен специально для acceptance case;
это не молчаливая замена двух местностей V3 или окончательная схема гейта.

| ID | Вмешательство / событие | Проверяемое наблюдение |
|---|---|---|
| R1 | Observed G− после frozen G+ | C0 получает ровно один nneg; duplicate receipt не добавляет второй. Origin C0 и прежний pf неизменны |
| R2 | Проверка только числа поддержки после R1 | p=2,nneg=1: 2/3>1/2. Один numeric admission ошибочно оставил бы C0 доступным после принятого уточнения; нужен отдельный вывод старой редакции из допуска |
| R3 | Уточнение принято по наблюдённому разделителю f=v | Старый K/C0 неизменён и полностью выведен из допуска; новые условия K0∧f=v и K0∧f≠v не пересекаются на известных f |
| R4 | Для нового контекста f неизвестен | Обе ветви unknown, даже при переменной x/n; не wildcard, не negative, без native dispatch до нужного match |
| R5 | Старый pending приходит после принятия уточнения | Оценка ровно его frozen G/редакции для аудита; это не возвращает C0 в допуск и не переносит evidence новым C |
| R6 | Разделитель не найден в уже наблюдённых признаках либо исчерпан лимит | Не придумывать скрытый f и не выбирать разделитель в driver; явно неуспех уточнения / INCOMPLETE по лимиту |
| R7 | Блок C или K, затем restore | Scoped guard действует до конкуренции, Q и dispatch; предложение до block/restore stale. Новый независимый достаточный C — отдельная redundancy, не восстановление заблокированного |

В R3 литерал t=c — один из доступных разделителей, а не переданная ядру
маска релевантности. x и n также изменились: порядок и бюджет поиска должны
дать реальную возможность найти и проверить t. Нельзя утверждать, что learner
обязан выбрать t сразу или что одна ошибка доказывает правильный разделитель.
Если выбран n или x, измерять последующие ошибки/уточнения в заданном бюджете.
Эта fixture не утверждает, что консолидация уже реализует нужный выбор.

## 3. Открытый вход протокола: origin дополнения

В §4 принятого дизайна уточнение создаёт частный K и дополнение старого
условия с новыми connecting Gen. По §6 origin — actual, вызвавший создание,
и p/n не наследуются. Эти правила исключают удобный, но неверный вариант:
засчитать противоречащий actual t=c,G− как positive origin дополнения t≠c,G+.
Этот actual не удовлетворяет ни его условию, ни продолжению. Старые positive
C0 также не становятся origin/прогнозами нового дополнения автоматически.

До полной пререгистрации требуется выбрать и принять точный жизненный цикл
дополнения. **Консервативное предложение, ещё не принято:** хранить предложенное
условие дополнения без поддержанного C; следующий подходящий actual вызывает
создание C с одним origin, и только последующий positive frozen forecast даёт
p=2. До этого native действие этого C недоступно. Нужно явно определить,
какой существующий механизм W хранит предложение, момент создания C и
бюджет curriculum; это не разрешение новой сущности или изменения N3a.

Критерий ревью R8: нельзя показывать оба дочерних C допущенными сразу после
одного противоречия. Для каждого — отдельные причинные origin/forecast,
без импорта p/n. Расчёт 4/8 actual/O покрывает создание/расширение из V3,
**не** конфликтное уточнение; переносить этот бюджет сюда нельзя.
Если origin/оценка дополнения остаются неоднозначными — протокол NOT_READY
по N5, а не «уточнение реализуем позже» после confirming.

## 4. G1: проверка ожидаемых ответов и цены

Для локального score fixture возьмём два доступных через A3 кандидата с
разными прогнозами: Kа содержит t=a, Kb содержит t=b. t ещё не прочитан;
оба K имеют unknown и рассматриваются G1, хотя native действие требует match.
Это проверка выбора чтения; сама по себе fixture не доказывает, что задача
имеет достижимую цель в обеих ветвях или что после чтения улучшится действие.

Публичный домен D(t)={a,b,c}; для Q_t цена 1, для Q_n цена 1. Меню и домены
одинаковы для arms. Число несовместимых пар в первых двух строках — ровно 1.

| ID | Набор / событие | Требуемый результат |
|---|---|---|
| Q1 | Ка:t=a, Kb:t=b | Допустимые ответы {a} и {b} не пересекаются: score(Q_t)=1/1=1; Q_n не разделяет пару: 0 |
| Q2 | Та же пара, цена Q_t=2 | Score=1/2; цена положительна и объявлена до выбора. Нулевая/неизвестная цена — не бесплатная проверка |
| Q3 | Ка:t≠a, Kb:t≠b | Ответы {b,c} и {a,c} пересекаются на c; пара не увеличивает score. При неизвестном домене также нет подтверждённого разделения |
| Q4 | Один кандидат имеет t=?x | Переменная не предсказывает конкретное значение; нет обоснованной непересекающейся пары с singleton. Недоступное t остаётся unknown |
| Q5 | Несколько точных клонов Ка/Kb | Тот же набор альтернатив и score; нельзя получить большинство клонированием. Дедупликация не объединяет разные настоящие альтернативы |
| Q6 | Равные максимальные score у двух Q | Abstain от Q по принятому baseline, без случайного tie-break. Random-Q — отдельная arm |
| Q7 | Оплаченная observed квитанция Q_t=a | Kb снимается только из текущего контекста; база и p/n прогнозов действий не меняются. Затем обычный A2/A3, без внешнего selector |
| Q8 | Unknown/interrupted/cancelled чтение | Ни один конкурент не устраняется как false, action evidence не добавляется; фактическая цена и статус записаны отдельно |
| Q9 | Кэш по тому же адресу/редакции либо исчерпан бюджет | Кэшированное наблюдение не новая независимая квитанция/evidence. Бюджет общий; платное новое чтение без разрешённого остатка не исполняется |
| Q10 | Заблокирован C/K/G либо изменена редакция | Guard до Q; stale предложение не использует старую квитанцию как соответствие новой редакции |

Контроли будущего опыта — no-Q, random-Q и baseline G1 при одинаковом
жёстком бюджете/меню/начальных наблюдениях. Ничего не компенсировать no-Q
бесплатным t. В отчёте: предложено/исполнено, cache hits, реально потрачено,
unknown и итог действия. Action accuracy/стоимость требуют отдельного
solvable curriculum с обеими операциями и целями; таблица score его не заменяет.

## 5. Проверка документа и следующий шаг

Статически проверены условия §4/§6–8 дизайна, границы 4/8 из V3, допуск N3a
и множества Q1–Q4. Воспроизводимая арифметика (Python, стандартная библиотека):

```python
from fractions import Fraction
assert Fraction(2, 3) > Fraction(1, 2)
assert not ({'a'} & {'b'})
assert ({'b', 'c'} & {'a', 'c'}) == {'c'}
assert Fraction(1, 2) == Fraction(1, 1) / 2
```

Это проверка логики примеров, не исполнение learner/evaluator и не новые
данные о FirstAGI. Ни seeds, ни старый debug не запускались. AC0 требует L
и T; v2 неизменен, closed публикуется также в L; протокол T до confirming L.

принятые cases в цельный AC0-T с окончательной кодировкой/доменами, split,
