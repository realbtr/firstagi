# Ревью 2026-11-10 · Поручение исполнителю: пакет K1 «Контракт периферии»

владельца; вступает в силу после слова владельца «принято» (с поправками, если
будут). До этого действует прежняя очередь, кроме протокола AC0-T: он отложен
указанием K1 ретро 10.11.

Заменяет в очереди пункт «цельный протокол AC0-T» из ревью 08.11. Z1–Z2 по PR41
остаются в силе.

## Почему именно это

Принцип владельца теперь записан (`docs/PRINCIPLE.md`, PR #42; дословные слова —
ретро 10.11). Главное расхождение с кодом лежит не в ядре, а в **периферии**:

- `drivers/base.py::PeripheralDriver` — пассивный источник токенов
  (`produce`, `query`). Он не возвращает тройку «команда, ключ, цель», не имеет
  собственных саккад с отчётом, обратного перехода, повышения разрешения с
  отказом.
- Ядро при этом уже близко к положениям 1–2: `core/feature.py` задаёт признак
  как относительный переход между областями, обобщения — цепочки.
- Стенд AC0 — плоский тор: на нём нельзя ни повысить разрешение, ни получить
  отказ, ни замкнуть цикл обратным переходом.

Поэтому самый полезный следующий шаг — дать ядру периферию, которая выражает
принцип, и проверить на ней один вопрос: **образуются ли замкнутые циклы и
находит ли ядро разрешающую характеристику в точке бифуркации**. Это
эмпирическая неизвестная, от которой зависит всё остальное. Новый протокол
для тора этот вопрос не проверяет.

Урок техретро 31.10 учтён: документ не должен заменить опыт. Поэтому пакет —
три коротких шага, из которых третий — код, и на каждом есть предел объёма.

## Шаг 1. Аудит «принцип → код» (без кода)

Таблица: положения 1–11 принципа × действующий код. Для каждого положения:
- где носитель (файл и функция) или «нет»;
- implemented / partial / missing;
- одна строка: что именно отсутствует.

Обязательно проверить и назвать по именам:
- что уже возвращает `StepResult` и чего не хватает до тройки;
- как `app/text_server.py::ActiveTextServer` (уровни масштаба, сдвиг, проба,

- какие части `core/proposal_loop.py`, `core/attention_loop.py`,
  `drivers/context_broker.py` уже выполняют задачи брокера (порядок обхода,
  место для команды);
- есть ли в `core/attractor.py::detect_bifurcation` то, что нужно положению 7.

Это source audit: читать код, не запускать опыты. Утверждение без ссылки на
файл и строку не засчитывается.

## Шаг 2. Дизайн-дельта контракта периферии (без кода)

Один файл `docs/design/PERIPHERY_CONTRACT_v0_1.md`, не больше 150 строк. В шапке
— какие положения принципа он операционализирует и какие нет.

Содержание:
1. **Контракт драйвера.** Отчёт как последовательность переходов (команда,
   ключ, цель, происхождение: рефлекс либо программа). Запросы ядра: обратный
   переход; повышение разрешения с исходами «удалось / не удалось»; программа
   команд, встраиваемая в текущий набор. Исход «не нашлось места» отличается от
   отказа и от отрицания. Ключ и цель непрозрачны для ядра.
2. **Минимальная периферия с вложенными областями.** Области образуют
   отношение включения (не обязательно дерево: область может входить в одну
   родительскую и не входить в другую). Три вида мест, заданных генератором и
   неизвестных ядру:
   - переходы однозначны — разрешение повышать незачем;
   - из одного ключа идут разные переходы, и вложенная область их разделяет;
   - переходы расходятся, а драйвер в повышении разрешения отказывает.
3. **Что должно сохраниться без изменений:** A1–A3, N3a, N5a–N5d, случаи
   приёмки PR36. Если что-то из этого придётся менять — стоп по N5 и вопрос
   ревьюеру, без правок.
4. **Таблица R1 — прогноз по построению.** Для каждого из трёх видов мест: что
   получит ядро при буквальной реализации и что получат контроли:
   - таблица с грубым фиксированным разрешением;
   - таблица с максимальным разрешением везде;
   - ядро без повышения разрешения.
   Две меры: качество прогноза перехода и число запросов разрешения (цена).
   Отдельной строкой: сколько циклов замкнётся и почему.
5. **Брокер.** Какая существующая часть берёт на себя порядок обхода и
   встраивание; что остаётся baseline с альтернативой.

Не включать: новые гейты, пороги, seeds, язык, наследование, положение 12.

## Шаг 3. Код периферии (без изменений `core/`)

Отдельный PR сразу после шага 2, **не дожидаясь его ревью**: периферия задана
прямыми словами владельца, а `core/` не трогается.

- Новый драйвер в `drivers/` с вложенными областями по шагу 2; генератор мест
  детерминирован по seed; подписи областей доступны только тестам.
- Тесты контракта на уровне драйвера: отчёт саккад без программы; встраивание
  программы и исход «не нашлось места»; обратный переход замыкает А→Б→А;
  повышение разрешения удаётся и не удаётся; происхождение каждого перехода
  указано; ядру не передаются подписи и включение областей.
- Один smoke-сценарий в `experiments/diagnostics/`: существующий
  `LearningSystem` получает поток переходов этого драйвера без программы и
  строит обобщения. В отчёт: число переходов, число замкнувшихся циклов, доля
  обобщений, подтверждённых более одного раза, visited records на шаг, байты
  состояния. Статус — smoke, не гейт; пороги не задаются.

Пределы: `core/`, протоколы, seeds 90101–90108 и 201–208 не трогать; confirming
закрыт; новых сущностей хранения не вводить; имена — по `docs/ONTOLOGY.md`
(раздел З-0122). Если для smoke потребуется изменить `core/` — остановиться и
записать, что именно мешает: это и есть результат шага.
